### Причина затягивания

Скрипт запускался из Git Bash на Windows. MSYS переписывает аргументы, похожие на POSIX-пути,
перед вызовом Windows-программы: `kubectl exec ... -- rm -f /data/fill.bin` превратился в
`rm -f "C:/Program Files/Git/data/fill.bin"` **внутри пода**. Такого файла нет, `rm -f` молча
вернул 0. Инструмент восстановления сообщил об успехе, не сделав ничего.

Первая попытка исправления (`MSYS_NO_PATHCONV=1` глобально) сломала другое: `curl -o /dev/null`
(нативный Windows curl) перестал работать, и скрипт решил, что Alertmanager недоступен.
Итоговое исправление — отключать конвертацию точечно для `kubectl exec` (`kexec` в `chaos/lib.sh`)
и переводить `KUBECONFIG` в Windows-форму через `cygpath`.

### Что сработало хорошо

- Алерт на причину (`RedisAOFWriteFailing`) сработал через 45 с после первой неудачной записи.
- Когда авария затянулась, сработала эскалация по симптомам и бюджету: сначала `BoutiqueHighErrorRate`,
  затем `SLOAvailabilityFastBurn` — ровно для этого и нужны многоуровневые алерты.
- Redis восстановился сам через 5 с после освобождения места — рестарт не понадобился.

### Что сработало плохо

- Действие по исправлению не проверяло свой результат: «команда вернула 0» ≠ «файл удалён».
- MTTD от заполнения диска — 141 с: Redis замечает проблему только при следующей записи AOF/RDB.
- Redis отклонял запись ещё и из-за `stop-writes-on-bgsave-error` (RDB-снапшот тоже не мог записаться).

| Действие | Тип | Статус |
